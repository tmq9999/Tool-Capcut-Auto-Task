# CapCut API map

## 1. Flow state machine

```text
NEW PROFILE
  -> www.capcut.com bootstrap (cookies, locale, log id)
  -> login iframe / passport region (CSRF + msToken)
  -> check email registered
  -> age-gate config + check_age_without_uid (#211/#220)
  -> send email code (capture includes request; OTP value is redacted)
  -> register_verify_login
  -> auth_broadcast
  -> set_birthday_by_uid (#235), later account-compliance reads
  -> user_info / account_info
  -> account/workspace/entitlement reads + LuckyCat baseline (#402)
  -> push reward (#1561) -> fresh LuckyCat snapshot (#1564)
  -> PWA reward (#1611) -> fresh LuckyCat snapshot (#1614)
  -> Firebase/FCM registration + cloudpush token update (#1849..1890)
  -> Try Inspiration reward (#1987) + product job (#1988..2065)
  -> Design children + parent reconciliation (#2423..2661)
  -> Creator children + parent reconciliation (#2746..2965)
  -> final LuckyCat snapshots (#2961, #2965, #3113)
```

This is observed request order, not a mandate to fabricate permission/install actions or a response-completion clock. The long-lived SSE request #2746 contains events produced after later message requests. The desired tool flow remains **signup/login -> check trial -> notifications -> install-Web -> Try Inspiration -> Design -> Creator -> reconcile**; the trace's delayed push registration is recorded, not silently reordered into a prerequisite. A signup path is present; existing-user password login is not.

## 2. Shared request envelope

Across first-party calls, the browser superset includes `Accept`, `Content-Type` (where present), `Origin`, `Referer`, `User-Agent`, locale/store headers, `appid`, and account/session cookies. Not every endpoint carries every field. Per-endpoint names/counts are in `endpoint-catalog.json`; global sources are in `headers-cookies.machine.json`. Minimum required fields are **unknown** until controlled verification.

The capture repeatedly contains `device-time`, `sign-ver`, `sign`, `x-secsdk-web-signature`, `x-secsdk-web-expire`, and security-client cookies/headers. Their presence is not evidence that a static replay value is valid. They must be generated by a supported client-state provider or the request must be blocked.

## 3. Bootstrap, auth and account

The authoritative per-endpoint catalog is `auth-trial-catalog.json`. The following sequence is the safe implementation boundary:

| Stage | Endpoint(s) observed | Purpose / input-output contract | State produced or consumed |
|---|---|---|---|
| Site bootstrap | `GET capcut.com/` (301), `GET www.capcut.com/` (200), `GET /login-embed` | Establish redirect, locale and browser cookies. | `ttwid`, `_tea_web_id`, `uifid`, `x_logid`, `capcut_locale`; do not copy from another account. |
| Region | `POST login-row.www.capcut.com/passport/web/region/`; same route on `login.us.capcut.com` | Form body contains observed `type`/`hashed_id` shape; response is a region/CSRF bootstrap. | `msToken`, `passport_csrf_token`, `passport_csrf_token_default`, deletion/region cookie events. |
| Email branch | `POST /passport/web/user/check_email_registered` | Select registration or login branch. Capture response had `is_registered=0`, `need_verify_email=0` for the observed new-account samples. | Passport CSRF header is equal to prior CSRF cookie in the capture. |
| Code request | `POST /passport/web/email/send_code/` | Sends a verification code to the user-supplied email. | OTP remains sensitive; do not log or put in fixtures. |
| Register/login | `POST /passport/web/email/register_verify_login/` | Consumes email/code/password registration fields and returns authenticated passport state. | Passport/account cookies and account identity; exact values are redacted. |
| Broadcast | `POST /passport/web/auth_broadcast/` on row/us hosts | Auth transition broadcast. | Session state and server cookie rotations. |
| Age gate | `POST www.capcut.com/lv/v1/sc/age_gate/get_age_gate_config`, `check_age_without_uid`, `set_birthday_by_uid`; later `check_u13_and_trigger_age_assurance` | Account compliance branch. A successful response only means the check completed. | Age/compliance state; UID may be response-derived. |
| User | `POST /lv/v1/user/web/user_info`, repeated `GET /passport/web/account/info/`, `POST edit-api.../lv/v1/user/web/authorized_user_info` | Retrieve account and authorization state used by later APIs. | `uid`, region, permission and subscription snapshots. |

Do not combine these response dialects: passport/account reads succeed here, but third-platform `authorized_user_info` #2802/#2994 returns HTTP200 with `ret="1904"` and `get authorized user info failed from third platform`. This is a linked-platform read failure, not evidence of failed CapCut signup or the cause of export problems.

The capture includes a request `x-tt-passport-csrf-token` that is blank on the region bootstrap and matches a prior CSRF cookie on the email branch. Do not assume blank is universally valid; preserve the per-request observed state and verify against a fresh account.

## 4. Trial / entitlement checks (read-only boundary)

The trial family contains read paths and a late commerce/checkout sequence. Read-only checks include the observed commerce endpoints:

- `commerce-api-sg.capcut.com/commerce/v1/subscription/user_info`
- `/commerce/v1/benefits/user_credit`
- `/commerce/v1/subscription/cc_web_price_list`
- `/commerce/v3/trade/subscription_infos`
- `/commerce/v1/resource_position`
- `/commerce/v3/resource/benefit_metadata`
- `/commerce/v1/subscription/get_subscribe_info`
- `/commerce/v1/subscription/batch_get`

All 35 captured subscription `user_info` responses have `ret=0`, `flag=false`, `is_free_trial=false`, `can_free_trial=false`, `can_free_trial_days=0`. Those fields describe the current user/subscription state; they are not a global offer-eligibility verdict. In #3163, `batch_get` stores its subresponses as JSON in the outer `response` string. After decoding that string, the first embedded price-list response has two offers whose `can_trial=true`, `trial_cycle=7`, `trial_cycle_unit=DAY`, and `trial_info.trial_price=0`. Thus the account is not currently in a trial but is eligible for captured 7-day, zero-price trial offers. See `trial-offer-correction.json` for the safe field paths. The capture also contains `/commerce/v3/trade/init_trade` (#3180), ten `query_trade` calls (all `order_status=PROCESSING`), cashier/pipopay and Google Pay traffic. No terminal payment/activation is observed. These calls are not authorized for automatic execution. Proposed read-only `checkEntitlement()` must distinguish current state from offer eligibility and remain separate from any explicitly approved, cost-fenced activation or purchase operation.

## 5. Workspace and first-party bootstrap

These calls are account-scoped prerequisites, not task completion:

- `POST edit-api-sg.capcut.com/cc/v1/workspace/get_all_everphoto_user`
- `POST .../mget_workspace_info`
- `POST .../get_user_workspaces`
- `POST .../get_member`, `check_create_workspace`, `sync_file_open_time`
- `POST .../lv/v1/user/web/user_permissions`
- `POST .../lv/v1/persona/get_questionnaire` and `/submit_questionnaire`
- `POST .../lv/v1/third_party_clouds/user_info`
- `POST .../lv/v1/notice/get_unread_count`
- `GET .../lv/v1/web/homepage/get_guide_show` and `POST .../record_guide_show`

For example, #278 `get_user_workspaces` returns `ret=0`, `workspace_infos`, `has_more=false` and `next_cursor`. The earlier request #277 `mget_workspace_info` already carries that workspace ID: exact comparison traces it to #237 `response.data.space_info.workspace_id`, not to the later #278 response. Store these IDs per account. HTML #250 `/my-edit` also contains JSON script `__GTW_USER_INFO__`; parsing its `__userInfoStringify` JSON produces `data.ever_photo.token`, exactly equal to `x-everphoto-global-session-token` sent by #983. This token differs from #237; stale reuse would be an incorrect source selection. See `bootstrap-state.machine.json`.

## 6. Notifications and install-Web

Notification-related calls are separate from task proof:

- `POST www.capcut.com/cloudpush/app_notice_status/` — form-shaped `aid`, `sender_id`, `platform=web_app`, notice/status values; response is a short message.
- `POST www.capcut.com/cloudpush/update_sender_token/` — form-shaped registration token; response is a short message.
- `POST firebaseinstallations.googleapis.com/...` and `POST fcmregistrations.googleapis.com/...` — external FCM registration dependencies.
- `POST edit-api.../lv/v1/start_page/get_tool_list`, `get_imc_resource`, `report_imc_open` — page/tool bootstrap and telemetry.

The capture proves push-registration HTTP exchanges and separate credited task states, not native permission or installation. The observed order is notice status #1527 -> push reward #1561/#1564 -> PWA reward #1611/#1614 -> Firebase/FCM #1849/#1884 -> sender token/status #1889/#1890. Do not call a reward endpoint as a substitute for actually enabling permission or installing an app. These two native effects require a separately proven HTTP-equivalent contract or an explicit product decision before HTTP-only migration.

## 7. Task catalog and generation jobs

### Authoritative 12-task reward ledger

Base: `https://edit-api-sg.capcut.com`.

| Operation | Exact endpoint | Observed contract / proof |
|---|---|---|
| Ledger read | `POST /luckycat/i18n/capcut/task/v1/task_list` | JSON `{scene}`; 34 responses, 12 keys each; no query fields; HTTP 200 and `err_no=0`; no Set-Cookie. Per-task states retained in `creator-tasks.machine.json`. |
| Reward mutation | `POST /luckycat/i18n/capcut/task/v1/do_action` | JSON `{action_key, op_id}`; query names `aid`, `device_platform`, `msToken`, `X-Bogus`, `X-Gnarly`; 9 calls, each distinct `op_id`; response `{err_no:0,err_tips:"",data:{}}`, Set-Cookie `msToken`. `op_id` generation/idempotency and query signing are not proven. |
| Campaign/task bootstrap | `POST /luckycat/i18n/capcut/campaign/v1/capcut/web/resource` | Six calls (#334…3108), signed query-name set as above; rewards/configuration, not ledger completion. |

Each mutation must have current-account provenance, task-specific product evidence and a **subsequent** successful LuckyCat ledger snapshot for that key. HTTP 200 or a reward status alone cannot prove a saved/generated/exported artifact. Do not synthesize parent actions; parent rows reconcile from their children.

### Common-task snapshot (not the reward ledger)

`POST edit-api-sg.capcut.com/lv/v1/common_task/list` appears 48 times. The capture requests status filters `[1]` and `[0,-1]`, cursor/count fields, and every response has `ret=0`, `common_tasks=[]`, `has_more=false`, `interval=30` in the observed session. This is a poll/snapshot API, not a mutation and not evidence that a task was completed.

### Try Inspiration: separate product generation chain

`POST /lv/v1/common_task/new` (**1988**) submits `enter_from=web_gen_ai_aigc`, `can_queue=true`, a `web_video_generate` `v3` task with prompt/image/template fields; response contains task ID/token, `status=queueing`, `failed_tasks=[]`. This is the **Try Inspiration product chain**, not the Creator-group generation contract.

The real follow-up is `POST /lv/v1/effect/genai/task/query` (20 calls, HTTP 200). The observed sequence is reward #1987 -> new job #1988 -> ledger #1993 already credited -> child processing #2003 -> #2056 `processing` with progress 100 -> #2065 `succeed` with progress 100 and opaque video/cover/download URL fields. Progress 100 alone is insufficient. The terminal response at #2065 proves server-side job success/locators, not a local verified download. `common_task/list` is not this job-result poller.

## 8. Try Inspiration and Design group

Design analysis covers all 344 design-family records plus 18 cross-family upload/ImageX records. The observed browser HTTP sequence is:

1. `POST /lv/v2/intelligence/inspiration/collection/list` (#2169, `{count:1,cursor:""}`) returns `resources=null`, `has_more=false`; `POST /lv/v2/intelligence/thread/inspiration/check` (#2266, empty body plus `aid/device_platform/region/web_id` query fields) returns `enable=false`. Both have success envelopes; neither proves feature/content availability. This Design gate is not the earlier Try Inspiration video job.
2. `POST /lv/v2/canvas/save` creates/updates the canvas and yields a canvas identifier/resource state.
3. `POST /lv/v2/intelligence/thread/create` consumes the canvas/resource ID.
4. `POST /lv/v2/intelligence/thread/run/start` returns the SSE response itself in two observed runs. Parse frames through `run_end`; `run_start` and HTTP 200 are nonterminal. The first run produces text; the second produces a JSON artifact (resource_type=9, 2048×2048) later bound by canvas saves.
5. `POST /lv/v2/intelligence/thread/detail` reads the thread state.
6. Image input branch: `POST /lv/v2/intelligence/file/chat_upload_sign` -> `GET www.capcut.com/ttuploader_proxy` (upload configuration) -> external TOS byte upload -> `POST /ttuploader_proxy` commit -> `POST /lv/v2/intelligence/thread/image_meta` -> `POST /lv/v2/canvas/save` binding.
7. `POST /lv/v2/canvas/upload_sign` -> ImageX request to obtain signing/session fields -> external TOS byte upload -> ImageX commit -> `POST /lv/v2/canvas/cover/update`. The capture repeats this cover sequence three times; the last update includes two cover URIs.

Upload domains (`tos-my216-share.vodupload.com`, `tos-my16-up.byteoversea.com`, `tos-my319-share.tiktokcdn.com`, `tos-my16-share.vodupload.com`) are returned storage dependencies, not interchangeable hard-coded endpoints. CapCut upload-sign responses supply temporary key material and session tokens. ImageX Apply replies supply upload host, store URI, SessionKey and TOS Auth. AWS-style `Authorization` is observed as a derived request field; its construction is not proved by returning credentials. Four `x-amz-content-sha256` headers (#2478/#2525/#2551/#2658) exactly equal SHA-256 of the outgoing body bytes, independently checked offline. This does not prove the full signing algorithm.

The design API acknowledgement, SSE completion and cover URI are not full task proof by themselves. Product evidence is terminal SSE + artifact references + relevant canvas save/detail evidence; a fresh LuckyCat task snapshot independently proves the reward ledger. Exact observed body fields, serialized `canvas_detail` revisions, commit linkage and response schemas are in [design-inspiration.md](./design-inspiration.md) and its machine file; these are observation variants, not proven required-field schemas.

## 9. Creator / Video group

Observed page and creator endpoints include:

- `GET /ai-creator/studio`, `GET /ai-creator/start` and page-resource/WASM dependencies.
- `POST /storyboard_agent/v1/ai_lab/send_msg`, `/poll_by_event_id`, `/get_conversations`.
- `POST /storyboard/v1/studio_draft/create_project`, `POST /storyboard/v1/studio_draft/fetch_latest_version`, `POST /storyboard/v1/get_lead_version`, `POST /storyboard/v1/agent/fetch_ideas`.
- `POST /storyboard_agent/v1/ai_lab/batch_query_assets`.

Create-project #2828 returns `draft_id` for later version reads and `send_msg.option.__project_id`. Normal `send_msg` #2874 and second `send_msg` #2905 with `credits_confirm` return success envelopes, not event IDs. SSE request #2746 starts with empty `event_id` and an unproven `session_id`; 48 events contain round/message/tool results including `generate_image`. Keep session, conversation, round, draft, version and tool task IDs local to one worker; do not invent an event-ID-return contract. Asset reads #2928/#2955 return images, and draft versions change by #2911/#2962. Neither is an exported video. Export proof requires a produced artifact and a fresh task snapshot; no captured universal export endpoint/minimum native export contract exists here.

### Twelve-task ledger

The 102 task records contain all 12 observed LuckyCat keys. Nine leaf actions have a captured `do_action`; registration was already status 4, and the Design/Video creation rows are parent rows that progress `1 -> 2 -> 4` after their children, without a fabricated parent action. The exact action IDs, status transitions and reward amounts are in [`creator-tasks.md`](./creator-tasks.md) and `creator-tasks.machine.json`. The most important boundary is `capcut_web_video_studio_export`: its reward reaches status 4, but no export/download/file response is captured, so the exported artifact remains unknown.

## 10. Telemetry, static and WebSocket coverage

The capture contains 1,207 telemetry records, static HTML/JS/WASM resources, security SDK reports, and nine `101` WebSocket handshakes at `frontier-sg.capcut.com/ws/v2`. Burp XML does not contain WebSocket frames, so the post-upgrade protocol is not mapped. These records are cataloged and hashed where large, but are not promoted to business-task requirements.

## 11. Implementation order after review

1. Build typed session/CookieJar and response validators from the safe catalogs.
2. Implement bootstrap/auth as a per-account state machine, with provider interfaces for CSRF, SDK tokens and signatures.
3. Implement read-only account/workspace/entitlement snapshots.
4. Implement one task adapter at a time: notification, install-Web, inspiration, design, creator. Each adapter has `prepare -> mutate -> verify` and a durable request/evidence ID.
5. After explicit authorization, use a controlled single-account native-HTTP probe with no payment. A new account and real operations have side effects; never call them merely because the probe says “test”. Use ablation only on independently approved requests and respect challenges/service limits.
6. Only after one account is proven, run two isolated workers, then three, and measure service rate limits. Scale to 10–20 only with bounded concurrency and per-worker backoff; never introduce a shared task queue that makes one worker wait on another worker's business task.
