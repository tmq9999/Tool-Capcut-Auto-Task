## Actual observed sequence

The capture is an email registration followed by authenticated commerce/subscription inspection and a payment handoff attempt. It is not evidence of an existing-user password login, a completed free trial, or a completed payment.

1. `81` — `GET www.capcut.com/login-embed` returns the login iframe/bootstrap HTML and initial web cookies.
2. `189/190` (OPTIONS), then `191/193` — region bootstrap on `login-row.www.capcut.com` and `login.us.capcut.com`; both POSTs return HTTP 200 and `message=success`, and set CSRF plus region-scoped cookies.
3. `194` (OPTIONS), then `196` and `209` — email registration checks. Both return HTTP 200, `message=success`, and `data.is_registered=0` (the capture therefore follows the new-registration branch, not existing-user login).
4. `222` (OPTIONS), then `224` — email-code request. HTTP 200, `message=success`; the request contains email/password fields and the response contains an email ticket, all redacted.
5. `228` (OPTIONS), then `230` — code verification + registration + login. HTTP 200, `message=success`, `data.status=1`, `data.new_user=1`, `data.has_password=0`. The request contains a `code` field, but its value is never printed. The response establishes session cookies.
6. `231/232` (OPTIONS), then `233/234` — auth broadcast to both login hosts; both HTTP 200 and `message=success`.
7. `244` and 117 subsequent `GET www.capcut.com/passport/web/account/info/` requests — authenticated account reads. HTTP 200 / `message=success`; the first response includes the newly established account state and `has_password` numeric field. Repeated polling/reads continue through the capture.
8. Starting at `260`/`261` and POST `279/280`, commerce bootstrap and subscription/benefit reads run repeatedly. All JSON commerce POSTs observed in this shard return `ret=0`, `errmsg=success`.
9. `3161/3163` — final subscription reads return `ret=0`, `errmsg=success`; `get_subscribe_info` has `data.subscribe_list=null` and an empty workspace subscription list. The outer `batch_get.data` is null, but decoding its JSON-encoded `response` reveals two offers with `can_trial=true`, a 7-day period and zero trial price.
10. `3177` then `3180` — `trade/init_trade` is called once and returns `ret=0`, `errmsg=success`. This is trade initialization/payment handoff, not trial activation proof.
11. `3182` then `3183,3202,3266,3272,3279,3287,3288,3290,3297,3300` — ten `trade/query_trade` polls return HTTP 200 / `ret=0` / `errmsg=success`, but every captured `data.order_status` is `PROCESSING`. No terminal paid/activated status is present.

## Header, cookie, and security provenance

- Auth requests consistently observed `appid`, `did`, and (after region bootstrap) `x-tt-passport-csrf-token`. The CSRF value in requests `196/224/230/233` exactly matches a prior `set-cookie` value from `193` by normalized reference; `did`/`web_id` exactly match the initial `_tea_web_id` set at `81`. These are equality observations only.
- Commerce POSTs commonly observed `appid`, `appvr`, `device-time`, `did`, `web_id`, `tdid`, `sign`, `sign-ver`, region/language fields, and authenticated cookies. `did`/`web_id` have a prior `_tea_web_id` source. `device-time` sometimes equals a prior JSON `systime`; `sign` has no prior-response source and is classified client-generated or otherwise unproven. `tdid` is present but empty in the representative requests and has no proven source. The catalog records per-endpoint counts and refs without revealing values.
- Cookie chronology is explicit in the machine catalog: initial web cookies at `81`; CSRF/`msToken` at `191/193`; region-reset cookies during registration checks; session cookies at `230`; region/target cookies then propagate to account and commerce calls. Attributes such as domain/path/max-age/secure/HttpOnly/SameSite are retained as names/flags only.
- `mssdk-sg.capcutapi.com/web/report` appears 14 times with JSON telemetry envelopes (`magic`, `version`, `dataType`, `strData`, `tspFromClient`) and `msToken`; it is not treated as an auth transition.

## Body/compression checks and proof limits

All 439 assigned auth/trial request and response bodies were read from raw offsets. Normalized states are: auth requests 126 empty / 8 form / 14 JSON; auth responses 7 empty / 140 JSON / 1 static HTML; trial requests 75 empty / 216 JSON; trial responses 71 empty / 220 JSON. Raw-item decompression state is `raw` for every assigned request and response; no `Content-Encoding` header was observed in this shard, so no gzip/Brotli decoding was needed.

There is no `/activate_trial`-like mutation in the assigned endpoints. The repeated `is_free_trial=false` / `can_free_trial=false` user-state responses establish that no trial was active at those reads, while decoded `batch_get` #3163 independently establishes two eligible 7-day, zero-price offers. The only trade mutation-like call is `init_trade`, followed by polling that remains `PROCESSING`; eligibility therefore must not be reported as activation. A single browser capture cannot prove server-required headers, a minimal replay set, signing algorithms, OTP validity beyond the successful observed request, or whether an eventual hosted payment would complete later.
